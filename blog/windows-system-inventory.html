Warum PowerShell mein Windows 11 als Windows 10 erkannte

Aus einer einfachen Inventarisierungsaufgabe wurde ein gutes Beispiel dafür, warum Admin-Datenquellen und Fehlerpfade bewusst geprüft werden müssen.

31. Juli 20268 MinutenPrivate Lab-Umgebung
Inhalt Das Ziel Zwei Antworten Das Skript Der Fehlerfall Automatisierte Tests Fazit

Das Ziel

Mein Testsystem ist eine private Windows-11-Pro-VM auf ARM64. Das Skript sollte Computername, Betriebssystem, Version, Build, Architektur und Erfassungszeitpunkt als PowerShell-Objekt liefern und zusätzlich in eine CSV-Datei schreiben.

Zwei Befehle, zwei Antworten

Meine erste Abfrage war Get-ComputerInfo. Dabei wurde das System als Windows 10 Pro, Version 2009, angezeigt. Das passte nicht zum installierten Windows 11.

Deshalb habe ich eine zweite Datenquelle geprüft:

Get-CimInstance -ClassName Win32_OperatingSystem |
    Select-Object Caption, Version, BuildNumber, OSArchitecture

CIM meldete korrekt Microsoft Windows 11 Pro, Version 10.0.26200 und Build 26200. Die interne Hauptversion 10.0 bleibt bei Windows 11 aus Kompatibilitätsgründen bestehen. Für das Inventarskript habe ich deshalb Win32_OperatingSystem als Datenquelle gewählt.

Vom Befehl zum wiederverwendbaren Skript

Die ermittelten Werte landen in einem PSCustomObject. Das Ergebnis ist dadurch nicht nur Konsolentext, sondern lässt sich filtern, weiterverarbeiten und zuverlässig als CSV exportieren.

$inventory = [pscustomobject]@{
    ComputerName    = $env:COMPUTERNAME
    OperatingSystem = $os.Caption
    Version         = $os.Version
    BuildNumber     = $os.BuildNumber
    Architecture    = $os.OSArchitecture
    CollectedAt     = Get-Date
}

Der Ausgabepfad ist ein Parameter. So kann dasselbe Skript unterschiedliche Zieldateien erzeugen, ohne den Quelltext zu verändern.

Der wichtige Test war der fehlgeschlagene

Danach habe ich absichtlich in einen nicht vorhandenen Ordner exportiert:

.\Get-SystemInventory.ps1 `
    -OutputPath .\missing-folder\inventory.csv

Export-Csv meldete zwar einen Fehler, das Skript gab anschließend aber weiterhin das Inventarobjekt aus. Das konnte wie ein Teilerfolg wirken, obwohl keine Datei geschrieben worden war.

Der Zielordner wird deshalb vor dem Export geprüft. Ein ungültiger Pfad beendet den Lauf kontrolliert. -ErrorAction Stop sorgt zusätzlich dafür, dass auch andere Schreibfehler terminieren.

$outputDirectory = Split-Path -Path $OutputPath -Parent

if ([string]::IsNullOrWhiteSpace($outputDirectory)) {
    $outputDirectory = '.'
}

if (-not (Test-Path -LiteralPath $outputDirectory -PathType Container)) {
    throw "Output directory does not exist: $outputDirectory"
}

Nicht nur manuell geprüft

Der finale Testlauf prüft fünf Anforderungen ohne zusätzliche PowerShell-Module:

  1. Das Objekt enthält den lokalen Computernamen.
  2. CIM erkennt Windows 11.
  3. Der CSV-Export erzeugt eine Datei.
  4. Nach Import-Csv bleibt die Buildnummer erhalten.
  5. Ein fehlender Zielordner erzeugt den erwarteten kontrollierten Fehler.

Was ich aus dem Lab mitnehme

Das Ergebnis ist kein Enterprise-Projekt. Es zeigt aber einen vollständigen technischen Ablauf: Anforderung verstehen, Datenquellen vergleichen, strukturiert implementieren, einen Fehler reproduzieren, die Ursache beheben und den Endstand automatisiert prüfen.

Gerade für Endpoint-Administration ist dieser Arbeitsstil wichtiger als ein einzelner Befehl. Das nächste getrennte Projekt wird einen lokalen Endpoint-Sicherheitsreport für TPM, Secure Boot und BitLocker aufbauen.
